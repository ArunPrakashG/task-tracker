# F7 Audit log in the background

## Summary

Every successful task status change is recorded in a `task_audit_logs` table, written in the background after the response has been sent. This is the fire-and-forget pattern: the PATCH returns immediately and never waits for, or fails because of, the audit write. The new table arrives as a second migration without touching the first.

## In scope

- `app/models/audit.py`: table `task_audit_logs`: `id` UUID PK, `task_id` UUID not null indexed, `project_id` UUID not null, `from_status`, `to_status` (same VARCHAR plus CHECK style as tasks), `changed_at` timestamptz not null. No foreign keys, so the history survives deletion of tasks and projects.
- Migration `alembic/versions/0002_task_audit_log.py`, generated with `uv run alembic revision --autogenerate -m "task audit log" --rev-id 0002`. Never edit `0001_initial_schema.py`; if the generated file is wrong, delete it and regenerate it before it is ever applied elsewhere. Do not create tables any other way.
- `app/handlers/audit.py`: `@on("task.status_changed")` handler that opens its own session from `async_session_factory`, calls `audit_service.record_status_change(session, payload)` and commits. Errors are logged and swallowed by the F1 dispatcher.
- Audit rows are only written after a successful transition, never after a rejected one.

## Out of scope

- Reading or exposing audit logs through the API. Other event handlers.
