# F8 Redis rate limiting

## Summary

Replace the F1 no-op `rate_limit` stub with a real Redis-backed sliding-window limiter, used as a decorator on the POST endpoints that F3 and F4 already decorate. Limits are read from settings at request time, so tests and deployments can change them without code edits.

## In scope

- `rate_limit(limit=None, window_seconds=None)` decorator for async route functions that declare `request: Request`. Defaults come from `settings.rate_limit_requests` and `settings.rate_limit_window_seconds`, read when the request arrives.
- Sliding window in Redis (sorted set per client and route, in a single atomic Lua script or transaction) using `redis.asyncio`, with the client created lazily from `settings.redis_url`. Key is the client IP plus the route path template, prefixed `ratelimit:`.
- Over the limit returns 429 with the common error envelope, code `RATE_LIMITED`, and a `Retry-After` header in seconds. Under the limit adds nothing visible.
- Fail open: if Redis is unreachable the request is allowed and a warning is logged.
- The decorated wrapper sets a marker attribute `__rate_limited__ = True` so a test can assert every POST route is protected.
- Only POST endpoints are decorated. GET and DELETE are not limited.

## Out of scope

- Per-user limits, burst allowances, other storage backends.

## Notes

- A local Redis is needed for these tests: `docker run -d --name redis -p 6379:6379 redis:7-alpine`. Tests use Redis database 15 and flush it between tests (provided by F9).
